❯ does it need eval dataset first? 

● No - behaviors and axes come before the dataset.

  Here's why:

  Wrong order:
  1. Create random test cases
  2. Figure out what you're testing
  3. Realize you're missing coverage

  Right order:
  1. Define behaviors you care about (routing, guardrails, etc.)
  2. Define axes to measure them on (correctness, safety, etc.)
  3. Then create dataset with cases that specifically test each behavior × axis
  combination

  Think of it like test-driven development:
  - You don't write random tests and hope they cover your code
  - You identify what needs testing, then write targeted tests

  For your Customer Support FTE:
  ┌────────────┬──────────────┬───────────────────────────────────────────────┐

● Let me break it down simply.

  Two questions determine the quadrant:

  1. How hard is it to CREATE test cases? (Easy vs Hard)
  2. How hard is it to GRADE the output? (Easy vs Hard)

                      GRADING
                  Easy    |    Hard
                ──────────┼──────────
          Easy  │   Q1    │    Q2
  CREATING      │         │
          Hard  │   Q3    │    Q4

  Q1: Easy to create, Easy to grade
  - Example: "What's 2+2?" → Check if answer == 4
  - Routing tests: "I need a refund" → Check if agent == BillingAgent

  Q2: Easy to create, Hard to grade
  - Example: "Explain our refund policy" → Need LLM to judge if explanation is
  good
  - You can write the query easily, but grading quality needs judgment

  Q3: Hard to create, Easy to grade
  - Example: Edge cases that need domain expertise to even think of
  - Like: rare billing scenarios only an accountant would know about
  - But once created, answer is clearly right/wrong

  Q4: Hard to create, Hard to grade
  - Complex scenarios needing expertise to create AND judge
  - Example: "Is this escalation-worthy?" - needs experience to know + judge

  ---
  For your routing tests:
  - Can you easily write queries like "I need a refund"? → Yes, easy to create
  - Can you check with code if it routed correctly? → Yes, easy to grade

  So routing tests are Q1, not Q3.

  Does that clarify it?

  Code-Based Grader Structure (Q1/Q3)

  def grade_response(output: str, expected: dict) -> dict:
      checks = {
          "has_required_fields": all(field in output for field in
  expected.get("required_fields", [])),
          "valid_json": is_valid_json(output),
          "within_length": len(output) <= expected.get("max_length", 1000),
          "no_pii_detected": not contains_pii(output),
          "matches_expected": output.strip() == expected.get("exact_match",
  "").strip()
      }

      score = sum(checks.values()) / len(checks)

      return {
          "passed": score >= expected.get("threshold", 0.8),
          "score": score,
          "checks": checks,
          "failed_checks": [k for k, v in checks.items() if not v]
      }

  Key pattern: Dictionary of checks → sum-based scoring → standardized output

  LLM Grader Structure (Q2/Q4)

  Critical insight: Use 5-7 binary YES/NO questions, not numeric scales.

  LLM_GRADER_PROMPT = """

  """

  Why binary over numeric: LLMs are good at classification but inconsistent at
  calibration (1-5 scales drift).
